# Specifications Grading

Source: Nilson LB (2015) Specifications Grading: Restoring Rigor, Motivating Students, and Saving Faculty Time. Stylus
Status: drafted from general knowledge of the work on 2026-09-02; cite-only book; Robert to review and correct.

## Main ideas

- Conventional points-based grading has known problems: partial credit
  rewards incomplete work, averaging hides whether any outcome was met,
  students negotiate points rather than learn, and grading consumes faculty
  time without improving learning.
- Specifications grading replaces partial credit with pass/fail judgments
  against clear specifications. Each assignment states exactly what an
  acceptable submission must contain and do; work that meets the specs
  passes, work that does not is returned. The bar for passing is set at
  what would normally be B-level or better work.
- Assignments are grouped into bundles, each bundle tied to a set of
  learning outcomes and to a course grade. Completing a more demanding
  bundle (more or harder assignments, higher-level outcomes) earns a higher
  grade. Students choose which grade to work for, which makes the workload
  and the outcome expectations explicit.
- Tokens give flexibility without negotiation: each student receives a few
  tokens to exchange for a late submission, a revision, or a missed
  low-stakes item. Tokens replace case-by-case exceptions.
- Specifications double as rubrics with one level: they describe the
  criteria of acceptable work in plain language, often as a checklist, and
  students can self-check before submitting.
- Because every passing assignment demonstrates an outcome, the grade means
  something: it records which outcomes were shown at which level, which
  fits constructive alignment and outcomes-based accreditation.
- Faculty time falls because grading becomes a yes/no check against specs
  and because fewer submissions need extended comments; feedback focuses on
  what is missing for the spec.
- The author discusses hybrid schemes (specs for some items, traditional
  grading for exams), how to convert an existing course, and how to explain
  the system to students on day one.

## What we take from it

- For project-based and programming courses in the group, publish
  specifications (checklists) for each deliverable and grade pass/fail
  against them; keep points-based grading for exams where it is required.
- Tie bundles to the outcomes in course.yaml so that the grade a student
  earns names the outcomes they have demonstrated.
- Use tokens for late work and resubmission instead of ad hoc extensions;
  write the token rule in the syllabus.
- Write specifications so that a student, or a script, can check them
  before submission; the rubric template in the course-design skill has a
  single-level specification variant for this purpose.
- Pair specifications grading with the KAUST letter-grade scale by
  publishing which bundle maps to which letter grade.
